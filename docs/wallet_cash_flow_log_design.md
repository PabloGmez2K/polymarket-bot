## Purpose

`tools/wallet_cash_flow_log.py` is a manual CLI for appending validated cash flow rows to `data/wallet_cash_flows.jsonl` in compliance with the attestation policy (`docs/wallet_cash_flows_policy.md`).

It answers one narrow question: did cash enter or leave the Polymarket wallet during a given period, and is that fact explicitly documented by Pablo?

It does not infer. It does not auto-populate. It does not unlock readiness by itself. Promotion of `wallet_pnl_7d` to canonical source requires separate Opus review and Pablo signoff regardless of the number of rows appended.

---

## Scope Constraints

The tool must NOT:

- Touch `bot.py` or any trading core.
- Import from `bot.py`.
- Interact with Railway, the live DB, or any remote resource.
- Send Telegram messages.
- Modify `alerts_state.json`.
- Change `canonical_source`, `bankroll_readiness`, or any readiness flag directly.
- Execute trades, sizing, or risk decisions.
- Accept `actor` values other than `pablo_manual`.
- Accept `type` values not in the allow-list.
- Auto-generate `period_start`/`period_end` without explicit user input.
- Accept a `--entry-id` override value starting with `EXAMPLE-` (testing-only override, if used, must not be a productive id).

## CLI Interface

```
python tools/wallet_cash_flow_log.py \
    --type <type> \
    --period-start <ISO-8601 UTC> \
    --period-end <ISO-8601 UTC> \
    [--note <free text>] \
    [--write] \
    [--init] \
    [--data-dir <path>] \
    [--entry-id <uuid4-override>]
```

`actor` is always hardcoded to `pablo_manual`. It is not a CLI argument.

`recorded_at` is always `datetime.utcnow().isoformat() + "Z"`. It is not a CLI argument.

`schema_version` is always `2`. It is not a CLI argument.

`entry_id` is always auto-generated by the CLI as UUID4. It is not a required CLI argument. A `--entry-id` override exists for testing purposes only and must not be used in production flows.

Without `--write`, the tool always runs in dry-run mode regardless of any other flags. Zero writes occur.

### Required arguments

| Argument | Description |
|---|---|
| `--type` | One of the allowed types (see below). |
| `--period-start` | ISO-8601 UTC timestamp or date for the start of the covered period. |
| `--period-end` | ISO-8601 UTC timestamp or date for the end of the covered period. |

### Optional arguments

| Argument | Default | Description |
|---|---|---|
| `--note` | `""` | Free text memo. Not used in readiness logic. |
| `--write` | false | Enable write mode. Without this flag the tool always runs dry-run regardless of other flags. |
| `--init` | false | Only valid with `--write`. Permits creating `data/wallet_cash_flows.jsonl` if it does not exist. Requires explicit textual confirmation before creating the file. |
| `--data-dir` | `data` | Directory for `wallet_cash_flows.jsonl`. |
| `--entry-id` | auto | **Testing-only override.** Must not be used in production. Auto-generated UUID4 is used when this flag is omitted. Override value must not start with `EXAMPLE-`. |

---

## Allowed Types

| Type | Meaning |
|---|---|
| `deposit` | Cash entered the wallet from outside Polymarket. |
| `withdrawal` | Cash left the wallet to outside Polymarket. |
| `no_cash_flow_attestation` | Pablo attests no deposit or withdrawal occurred during the period. |
| `adjustment` | An explicitly reviewed correction. Requires a `--note` explaining the reason. Blocks readiness until human review confirms it. |

Forbidden types (must be rejected with a clear error):

- `inferred`
- `auto`
- `reconstructed`
- `estimated`

Any unlisted type must also be rejected.

## Output Row (Schema v2)

```json
{
  "schema_version": 2,
  "entry_id": "<auto-generated UUID4>",
  "recorded_at": "<utcnow ISO-8601>Z",
  "actor": "pablo_manual",
  "type": "<validated type>",
  "period_start": "<provided>",
  "period_end": "<provided>",
  "note": "<provided or empty>"
}
```

## Validation Rules (Pre-Write)

1. `--type` must be in the allow-list. Reject otherwise.
2. `period_start` must be parseable as ISO-8601. Reject otherwise.
3. `period_end` must be parseable as ISO-8601. Reject otherwise.
4. `period_end` must be after or equal to `period_start`. Reject otherwise.
5. `type == "adjustment"` requires `--note` to be non-empty. Reject otherwise.
6. If `--entry-id` override is used (testing only), the value must not start with `EXAMPLE-`. Reject otherwise.
7. The auto-generated UUID4 `entry_id` must not already exist in the file (collision guard). Reject otherwise. This also applies to the `--entry-id` override.
8. Before any append, the tool must re-read and validate every existing row in the file. If any existing row fails schema v2 validation (missing required fields, wrong `schema_version`, forbidden `type`, or missing `actor`), **abort without writing**. Corrupt or invalid existing rows are a hard stop — the file must be manually repaired before new rows can be appended.

---

## Default Behavior: Dry-Run

Without `--write`, the tool always runs in dry-run mode. This is the safe default.

- All validations run (input, existing file rows, schema v2 check).
- The output row is printed as formatted JSON to stdout.
- A line is printed: `DRY-RUN: row NOT written.`
- No file is created or modified under any circumstance.
- Exit code 0 if validation passes, nonzero otherwise.

---

## Write Mode (`--write`)

When `--write` is passed:

- If `data/wallet_cash_flows.jsonl` does not exist, **abort with an error** unless `--init` is also passed.
- Run all validations, including the full re-read and schema v2 check of every existing row. Abort on any failure.
- Append the validated row as a single JSON line.
- Print: `APPENDED entry_id=<id> to <path>`.
- Print the row for audit visibility.
- Exit code 0.

---

## Init Mode (`--write --init`)

`--init` is only valid together with `--write`. Using `--init` without `--write` is rejected with an error.

When both `--write` and `--init` are passed and the file does not exist:

- Print a warning: `INIT: data/wallet_cash_flows.jsonl does not exist and will be created.`
- Require explicit textual confirmation from the user: print `Type YES I CONFIRM to proceed:` and read stdin.
- If the user does not type `YES I CONFIRM` exactly, abort without creating the file.
- On confirmation: create the file, append the validated row, print `APPENDED entry_id=<id> to <path>`.
- Exit code 0.

- No Telegram call.
